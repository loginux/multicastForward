# 组播隧道协议规格（MCFW/1）

| 项目 | 内容 |
| --- | --- |
| 协议名称 | MCFW（Multicast Forward） |
| 协议线格式版本 | `0x01` |
| 文档版本 | v0.1（草案） |
| 对应需求 | 《组播隧道需求规格说明书》v0.5 第 5 章 |
| 文档状态 | 待评审 |
| 适用 | 主机 A（TCP 客户端）与主机 B（TCP 服务端）之间的单向隧道 |

## 1 适用范围

本协议描述主机 A 与主机 B 之间在一条 TCP 连接上的**握手认证**与**数据/控制帧**格式，使 A 侧接收的 UDP 组播载荷能以原有边界逐字节送达 B 侧并重新组播发出。

不涉及：组播组地址、端口、TTL、网卡等参数——这些全部由两端各自的配置文件决定，**协议中不携带任何组播参数**。也不涉及 A 与组播源之间、B 与接收者之间的 UDP 行为。

> 本协议与承载程序的形态无关：图形界面版（`multicastForward`，按角色切换）与控制台版（`mc_forward_a` / `mc_forward_b`）共用同一份编解码与认证实现，线格式完全一致，可任意组合互通。

## 2 约定

### 2.1 字节序

所有多字节整数字段一律**大端**（网络字节序）。

### 2.2 单位

- 长度单位统一为字节。
- 表中「偏移」以该报文起始位置为 0。

### 2.3 关键常量

| 名称 | 值 | 说明 |
| --- | --- | --- |
| `MAGIC` | `4D 43 46 57` | ASCII `MCFW` |
| `VERSION` | `0x01` | 当前唯一支持版本 |
| `HELLO_LEN` | 8 | |
| `CHALLENGE_LEN` | 16 | |
| `AUTH_LEN` | 32 | SHA-256 输出长度 |
| `AUTH_RESULT_LEN` | 1 | |
| `HEADER_LEN` | 3 | 帧头：1 + 2 |
| `MIN_PAYLOAD` | 1 | 数据帧载荷下限 |
| `MAX_PAYLOAD` | 1024 | 数据帧载荷上限 |
| `MAX_FRAME` | 1027 | `3 + 1024` |
| `TYPE_DATA` | `0x01` | |
| `TYPE_PING` | `0x02` | |
| `TYPE_PONG` | `0x03` | |

### 2.4 承载假设

- 底层为 TCP，提供可靠、有序、无重复、无消息边界的字节流。
- 因此本协议**不做**重传、序号、校验和、排序。任何「丢包」都源于上层主动丢弃（队列满、超长包、背压），而非协议缺陷。
- 一条 TCP 连接对应一次会话；连接关闭即会话结束，无独立拆链报文。

## 3 会话生命周期

### 3.1 状态

| 状态 | 侧 | 含义 |
| --- | --- | --- |
| `CLOSED` | 双 | 无连接 |
| `CONNECTING` | A | TCP 握手中 |
| `HANDSHAKE` | 双 | TCP 已建立，认证未完成 |
| `ESTABLISHED` | 双 | 认证通过，可收发数据帧 |
| `BACKOFF` | A | 等待重连 |

### 3.2 时序

```text
   主机 A (client)                          主机 B (server)
        |                                          |
        |   TCP 三次握手（不在本协议范围内）          |
        |<---------------------------------------->|
        |                                          |
        |   ---- HELLO (8B) -------------------->  |   B 校验 magic/version/flags
        |   <--- CHALLENGE (16B) ---------------   |   B 生成 nonce
        |   ---- AUTH (32B) ------------------->   |   B 常量时间比较
        |   <--- AUTH_RESULT (1B) --------------   |   0x00 成功 / 0x01 失败
        |                                          |
        |   ===== ESTABLISHED，双向发帧 =====       |
        |   ---- DATA (3+1..1024) -------------->  |   B 解帧后组播发出
        |   ---- PING (3B) --------------------->  |   每 10s
        |   <--- PONG (3B) ---------------------   |
        |                                          |
        |   ---- FIN / RST --------------------->  |   会话结束（无专用报文）
```

### 3.3 阶段约束

| 约束 | 说明 |
| --- | --- |
| 握手先于数据 | `ESTABLISHED` 之前，任一方发送 DATA/PING/PONG 均视为协议违规，接收方断开 |
| 握手不可重入 | 一条连接只进行一次握手；失败即关闭连接，重试需新建 TCP 连接 |
| 握手中无帧格式 | 握手四个报文均为定长，不使用 `type + length + payload` 结构，接收方按固定长度读取 |
| 单向认证 | 仅 B 验证 A。A 不验证 B，也不发送任何身份信息 |

## 4 握手报文

### 4.1 HELLO（A → B，8 字节）

| 偏移 | 长度 | 字段 | 取值 |
| --- | --- | --- | --- |
| 0 | 4 | `magic` | 固定 `4D 43 46 57` |
| 4 | 1 | `version` | `0x01` |
| 5 | 1 | `flags` | 必须为 `0x00` |
| 6 | 2 | `reserved` | 必须为 `0x00 0x00` |

B 的校验：magic 不匹配、version 不等于 `0x01`、`flags` 或 `reserved` 非 0 —— 任一成立即**直接关闭连接**，不发送任何响应（见附录 A 的改进建议 A1）。

A 发出 HELLO 后立即进入等待 CHALLENGE 状态，不做超时重发（握手整体 5 秒超时统一处理）。

### 4.2 CHALLENGE（B → A，16 字节）

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `nonce` | 16 | 密码学安全随机数 |

要求：

- 每次连接由 `crypto/rand` 等价接口生成，**禁止**复用、禁止可预测。
- 无结构、无填充、无长度前缀，就是一串 16 字节。
- 每条连接只发一次。

### 4.3 AUTH（A → B，32 字节）

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `hmac` | 32 | 见下方计算方式 |

计算方式：

```text
message = "MCFW" || version || nonce
          4B       1B        16B
        = 21 字节

hmac    = HMAC-SHA256(key = password_utf8, message = message)
          32 字节，按原样传输，不做十六进制或 Base64 编码
```

其中：

- `password_utf8` 为配置项 `[auth] password` 的 UTF-8 编码字节序列，**不做** Unicode 规范化、不做大小写折叠、不加盐、不做 KDF。
- `version` 为 `0x01`，即 HELLO 中携带的版本字节。
- `"MCFW"` 为 ASCII 或十六进制 `4D 43 46 57`。

B 的校验：

- 用自身口令重算 HMAC，与收到的 32 字节做**常量时间**比较（如逐字节异或累加后判零），禁止使用 `memcmp` 之外的短路比较。
- 比较前先确认收到满 32 字节，不足则在握手超时后关闭。

### 4.4 AUTH_RESULT（B → A，1 字节）

| 值 | 含义 | 后续 |
| --- | --- | --- |
| `0x00` | 认证成功 | 双方进入 `ESTABLISHED` |
| `0x01` | 认证失败 | B 发送后立即关闭连接；A 收到后转入退避重连 |
| 其他 | 未定义 | 收到方按认证失败处理并关闭 |

B 发送 `0x01` 后应至少将该字节写出到内核缓冲区再关闭，避免 `SO_LINGER` 默认行为导致 RST 把最后一个字节吞掉。实现上先 `write()` + `flush()`，再 `disconnectFromHost()`。

对外日志不得区分「口令错」与「未知原因」，仅记录失败次数（需求 FR-B4）。

### 4.5 握手时序要求

| 事件 | 超时 |
| --- | --- |
| TCP 建立 → 收到 HELLO | 5 秒 |
| 发 CHALLENGE → 收到完整 AUTH | 5 秒 |
| 全程（TCP 建立 → AUTH_RESULT） | 5 秒 |

超时的处理：双方均主动关闭连接。A 进入退避重连。

## 5 帧格式

### 5.1 通用帧头

`ESTABLISHED` 之后的所有报文（A→B、B→A）均采用：

```text
+--------+------------------+---------------------------+
|  type  |      length      |          payload          |
|  1 字节 | 2 字节（大端）    |  0 或 1..1024 字节         |
+--------+------------------+---------------------------+
  偏移 0      偏移 1..2            偏移 3 起
```

| 字段 | 长度 | 取值范围 |
| --- | --- | --- |
| `type` | 1 | `0x01` / `0x02` / `0x03` |
| `length` | 2 | DATA：1–1024；PING/PONG：必须为 0 |
| `payload` | `length` | 字节序列 |

### 5.2 DATA（`0x01`，A → B）

| 项 | 规则 |
| --- | --- |
| 方向 | 仅 A → B。B 收到 DATA 属违规（B 不向 A 送数据） |
| `length` | 1–1024。0 或 >1024 均为非法 |
| `payload` | A 侧收到的 UDP 载荷原样，**逐字节一致**，不压缩、不加头、不改序 |
| 边界 | 一个 DATA 帧恰好对应一个 UDP 报文；接收端不得合并或拆分 |

B 收到后的动作：将 `payload` 作为单个 UDP 报文，从配置的出口网卡、以配置的组地址/端口/TTL/回环设置发出。源 IP 为出口网卡地址，源端口由系统分配。

### 5.3 PING（`0x02`）/ PONG（`0x03`）

| 项 | 规则 |
| --- | --- |
| `length` | 必须为 0 |
| 方向 | PING 仅 A → B；PONG 仅 B → A |
| 语义 | 仅作存活探测，不带时间戳、不带序号，不用于 RTT 统计 |
| 响应 | B 收到 PING 立即回 PONG（同一条连接） |

A 的判定：每 10 秒发一个 PING，连续 3 次（30 秒）未收到任何 PONG，判定连接失效，主动 `abort()` 并重连。

B 的判定：记录「最后一次收到任意帧」的时间戳，超过 `runtime.heartbeat_timeout`（默认 30 秒，建议 40 秒）未收到任何帧，判定对端失联，关闭连接。

### 5.4 各类型汇总

| type | 名称 | 方向 | length | payload |
| --- | --- | --- | --- | --- |
| `0x01` | DATA | A → B | 1–1024 | UDP 载荷原样 |
| `0x02` | PING | A → B | 0 | 无 |
| `0x03` | PONG | B → A | 0 | 无 |
| `0x10`–`0x13` | 远程更新 | 双向 | 见 5.5 | 见 5.5 |
| 其他 | — | 双向 | — | 非法，见 7.2 |

### 5.5 远程更新（`0x10`–`0x13`）

> 可选能力，仅在 A 主动发起「更新服务端程序」时使用，不参与日常转发。

传输复用同一条 TCP 连接，**固定 1 KB 一包**：与数据帧同量级，不触碰 UDP MTU，也不需要放大接收缓冲（缓冲上界仍是 4 KB）。

| type | 名称 | 方向 | length | 说明 |
| --- | --- | --- | --- | --- |
| `0x10` | UPDATE_BEGIN | A → B | 36 | 4 字节文件总长 + 32 字节 SHA-256 |
| `0x11` | UPDATE_CHUNK | A → B | 5–1028 | 4 字节偏移 + 1–1024 字节数据 |
| `0x12` | UPDATE_END | A → B | 0 | 传输结束 |
| `0x13` | UPDATE_RESULT | B → A | 1–256 | 1 字节结果码 + UTF-8 说明 |

UPDATE_BEGIN 载荷（36 字节）：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 | 文件总长度，大端 |
| 4 | 32 | 整个文件的 SHA-256 |

UPDATE_CHUNK 载荷：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 | 本块在文件中的偏移，大端；必须等于已接收字节数 |
| 4 | 1–1024 | 数据 |

UPDATE_RESULT 结果码：

| 值 | 含义 |
| --- | --- |
| `0x00` | 校验通过，服务端即将重启 |
| `0x01` | 长度不符或 SHA-256 不一致，已丢弃 |
| `0x02` | 落盘失败 |
| `0x03` | 请求非法（未先发 BEGIN、偏移不连续、超出声明长度） |
| `0x04` | 已有更新正在传输 |

实现约束：

- 服务端**不接受客户端指定的文件名**，始终写入自身同目录的 `multicastForward.exe.new`，避免路径注入。
- 偏移必须严格连续；乱序、越界或超过声明长度，立即以 `0x03` 拒绝并删除暂存文件。
- 只有 SHA-256 校验通过才启动「启动器」执行替换；校验失败不改动现有 exe。
- 服务端随后以正常退出结束进程，由启动器完成「备份 → 替换 → 启动 → 存活检测 → 失败回滚」。
- 更新完成后连接会断开，A 按常规重连逻辑恢复转发。

## 6 接收与解帧规则

### 6.1 字节流累积

TCP 不保证一次 `read` 得到一个完整帧，必须做增量解析：

```text
缓冲区 ← 追加本次读到的所有字节
循环：
    若 缓冲长度 < 3           → 退出循环，等待更多数据
    type ← buf[0]
    若 type 非 {01,02,03}     → 非法，断开连接（无法确定帧边界）
    length ← 大端(buf[1], buf[2])
    若 type==DATA 且 (length==0 或 length>1024) → 非法，断开
    若 type∈{PING,PONG} 且 length!=0              → 非法，断开
    若 缓冲长度 < 3 + length  → 退出循环，等待更多数据
    payload ← buf[3 .. 3+length)
    从缓冲移除前 3+length 字节
    交付 payload
```

要点：

- 先校验 `type`，再读 `length`。因为未知 `type` 意味着无法判断该帧有多长，只能立即断开——这也是「未知类型即非法」的实现理由。
- 必须循环解析，一次读入可能包含 0 个、1 个或多个完整帧。
- 不得按 `length` 预分配超过 1027 字节的缓冲。

### 6.2 缓冲上界

| 条件 | 动作 |
| --- | --- |
| 缓冲长度 ≤ 1027 且不完整 | 正常等待 |
| 缓冲长度 > 1027 + 读入窗口（取 4096）仍无法解出帧 | 判非法，断开 |

该上界防止对端持续发送不完整帧把接收方内存撑大。

### 6.3 半包与断连

连接在帧中途关闭时，残留的半个帧直接丢弃，记 warn 日志（含已缓冲字节数），不影响后续重连。

## 7 合法性判定

### 7.1 握手阶段

| 条件 | 发送方 | 接收方动作 | 日志级别 |
| --- | --- | --- | --- |
| magic ≠ `MCFW` | A | B 关闭连接 | info |
| version ≠ `0x01` | A | B 关闭连接 | info |
| `flags` ≠ 0 | A | B 关闭连接 | info |
| `reserved` ≠ 0 | A | B 关闭连接 | info |
| 5 秒未完成握手 | 双 | 各自关闭 | warn |
| AUTH 值不匹配 | A | B 回 `0x01` 并关闭 | warn |
| AUTH 后收到非 `0x00/0x01` | B | A 按失败处理并关闭 | warn |

### 7.2 传输阶段

| 条件 | 动作 | 日志级别 |
| --- | --- | --- |
| 未知 `type` | 断开连接 | error |
| DATA 帧 `length == 0` | 断开连接 | error |
| DATA 帧 `length > 1024` | 断开连接 | error |
| PING/PONG 帧 `length != 0` | 断开连接 | error |
| UPDATE 帧长度越界 | 断开连接 | error |
| UPDATE_CHUNK 偏移不连续 | 回 `0x03` 并丢弃暂存文件，不断连接 | warn |
| B 收到 DATA（方向错误） | 断开连接 | error |
| A 收到 PING（方向错误） | 断开连接 | warn |
| 缓冲超上界 | 断开连接 | error |
| 心跳超时 | 断开连接 | warn |

注意区分两类「超长」：

- **UDP 层超长**（>1024 字节的组播报文）：A 侧在收包时丢弃并计数，**不进入协议**，也不产生任何帧。
- **帧层超长**（`length > 1024`）：属协议违规，B 侧断开连接。正常实现下前者已被 A 挡住，后者只可能来自异常或恶意对端。

### 7.3 断开动作统一要求

- 关闭 socket 前不再发送任何数据（`AUTH_RESULT` 是唯一例外，见 4.4）。
- 记录「原因 + 对端地址 + 已传输帧数」，原因文本不得包含口令或完整 HMAC。
- 清理该连接的会话状态与缓冲；**不得**影响其他连接与监听状态。

## 8 定时器

| 名称 | 侧 | 默认值 | 触发动作 |
| --- | --- | --- | --- |
| 握手超时 | 双 | 5 s | 关闭连接 |
| PING 周期 | A | 10 s | 发送 PING |
| PONG 超时 | A | 30 s（3 次） | 判定失效，重连 |
| 心跳超时 | B | 30 s（建议 40 s） | 关闭连接 |
| 连接重试 | A | 固定 3 s | 重连 |
| 认证失败退避 | A | 固定 30 s | 重连 |
| 统计上报 | 双 | 60 s | info 日志 |

所有定时器基于 `QTimer` 与单调时钟（`QElapsedTimer`），不依赖系统墙钟。

## 9 版本策略

| 规则 | 说明 |
| --- | --- |
| 版本号位置 | 仅 HELLO 的 `version` 字节 |
| 兼容判定 | 只有线格式不兼容时才提升版本号；新增可选能力优先用 `flags` 位扩展 |
| v1 行为 | B 只接受 `0x01`，其余直接关闭 |
| 向前兼容 | 无。A 与 B 必须同时升级到同一版本 |
| 未来扩展位 | `flags` 目前全 0，预留给「压缩」「双向」等能力协商 |

由于两端同时部署、同时升级，v1 不做版本协商与降级。

## 10 安全考量

| 威胁 | 现状 | 说明 |
| --- | --- | --- |
| 口令明文传输 | 已避免 | 挑战应答，线路上只有 HMAC 结果 |
| 重放认证 | 已避免 | nonce 每连接随机，且握手只在新建 TCP 连接时进行一次 |
| 时序侧信道 | 已避免 | HMAC 比较使用常量时间实现 |
| 暴力破解 | 部分缓解 | 连续认证失败增加 1 秒延迟；无锁定、无速率上限 |
| 传输窃听 | **未防护** | v1 不加密，载荷与帧头均明文，仅限内网 |
| 中间人 | **未防护** | 单向认证，A 不验证 B |
| 口令存储 | 明文 | 依赖文件系统权限；日志与统计中不得出现 |
| 拒绝服务 | 部分缓解 | B 侧握手中连接上限 8；无 IP 黑名单 |
| 远程更新被滥用 | **高风险，未设开关** | 任何通过认证的对端都能替换服务端 exe，等同于取得该主机的程序执行权。当前实现按需求「始终允许更新」，必须配合强口令、限制端口可达范围，并保留 `launcher.log` 审计 |

补充要求：

- 口令为 UTF-8 字节参与 HMAC。若含非 ASCII 字符，两端配置文件的字符编码必须一致（统一 UTF-8 无 BOM），否则会静默认证失败。
- 日志中 HMAC 最多输出前 3 字节加 `...`，或仅输出「len=32」。
- 不得在命令行参数、进程标题、配置文件注释中出现口令。

### 11.2 AUTH

输入：


## 附录 A 待确认变更

以下为在编写本协议时发现的、需求规格 v0.4 未覆盖或存在矛盾的点。**当前正文均按需求原文实现**，建议项需评审后决定是否纳入。

| 编号 | 问题 | 建议 |
| --- | --- | --- |
| A1 | HELLO 校验失败时 B 直接关连接，A 只能看到 EOF，无法区分「版本不符」「magic 不符」与「口令错」，会以 30 秒退避无限重连且日志无有效信息 | 增加 `REJECT`（`type=0x04`，payload 为错误码）作为关闭前的最后一帧；或至少让 B 侧日志区分原因、由运维比对。新增 type 属不兼容变更，宜随 v2 发布 |
| A2 | A 的 PONG 超时（30 s）与 B 的心跳超时（30 s）相等，两端可能同时判定对端死亡 | B 侧改为 40 s，让 A 先发现并主动重连。属配置默认值调整，不影响线格式 |
| A3 | 无会话结束报文，关闭原因无法传达 | v1 可接受（TCP FIN 足够）；若后续需区分「主动下线」与「异常断开」，可加 `GOODBYE`（`0x05`） |
| A4 | `AUTH_RESULT` 仅 1 字节，无错误明细 | 与 A1 合并处理：用 1 字节取值区分（`0x02` 版本不支持、`0x03` 协议非法），现有取值不变，向后兼容 |
| A5 | 数据帧 `length` 上限写死 1024，未来若要放大需改版本 | 保持；放大上限属不兼容变更，必须提升 `version` |
| A6 | 未定义「同一 TCP 连接上 A 收到 DATA」的处理 | 正文 7.2 已按「方向错误即断开」处理，建议补入需求文档 |
