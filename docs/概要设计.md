## 1 引言

### 1.1 目的

本文档在需求规格 v0.4 的基础上，给出组播隧道的总体结构、模块划分、关键机制、接口与数据结构设计，作为详细设计与编码的依据。

### 1.2 范围

覆盖 v1 范围内的两端程序及一个测试用发包工具。不覆盖双向隧道、多客户端、多组复用、TLS、GUI、系统服务。

### 1.3 术语

沿用需求规格第 2 章。本文档新增：

| 术语 | 说明 |
| --- | --- |
| 帧（Frame） | 隧道协议在 TCP 上传输的最小单位，`type + length + payload` |
| 发送泵（Pump） | 把队列中的帧写入 TCP socket 的调度逻辑 |
| 高水位（High Watermark） | TCP 待发字节上限，超过即暂停发送泵 |
| 活动会话 | B 侧当前正在转发数据的唯一连接 |
| 握手中连接 | B 侧已建立 TCP 但尚未完成认证的连接，不参与转发 |

1. 《组播隧道需求规格说明书》v0.4

## 2 总体设计

### 2.1 设计目标与约束

| 类别 | 约束 | 设计含义 |
| --- | --- | --- |
| 拓扑 | 1 对 1 单向 | 不需要路由表、会话索引、多路复用 |
| 负载 | 1–100 包/秒，≤1024 B/包 | 峰值约 0.8 Mbps，单线程足够 |
| 平台 | Windows / Linux 同一套代码 | 排除 MFC、排除平台专用 API 作为主路径 |
| 交付 | 控制台程序，不做服务 | 无 GUI 依赖，Qt 只链 Core + Network |
| 内存 | 常驻 ≤50 MB | 自管队列容量固定，禁止无界缓冲 |
| 可靠性 | 7×24 运行，断线自愈 | 所有异常路径必须回到可重连状态 |

### 2.3 系统结构与分层

```text
+-----------------------------------------------------------+
|  入口层   multicastForward（主交付，单窗口）                   |
|           main_a.cpp / main_b.cpp（控制台版，可选）          |
+-----------------------------------------------------------+
|  界面层   MainWindow                                     |
|           （角色切换、参数表单、导入导出、状态与日志）        |
+-----------------------------------------------------------+
|  应用层   TunnelClient              TunnelServer          |
|           （连接状态机、握手、心跳）  （会话管理、替换、超时） |
|           MulticastReceiver         MulticastSender       |
|           （入组、过滤、超长丢弃）    （出口网卡、TTL、回环） |
+-----------------------------------------------------------+
|  通用层   Config      Log       Stats      Protocol       |
|           （INI 读写/校验）（分级/脱敏/回调）（计数）（编解码/HMAC） |
+-----------------------------------------------------------+
|  平台层   Qt 5.15 Core / Network / Widgets -> Winsock / BSD |
+-----------------------------------------------------------+
```

分层规则：

- 界面层只调用应用层暴露的启动/停止与统计接口，不直接操作 socket。
- 应用层与通用层保持无界面依赖，同一份实现同时供 GUI 与控制台版使用。
- 平台差异全部收敛在 Qt 之内，业务代码不出现 `#ifdef _WIN32`。

### 2.6 远程更新流程

更新是叠加在现有单线程事件驱动之上的可选能力，不改变日常转发路径：

1. 客户端在菜单「工具 → 远程更新服务端…」发起，先停止转发，选择本地 exe；
2. `UpdateClient` 建立独立 TCP 连接，复用 HELLO / CHALLENGE / AUTH 完成认证；
3. 发送 `UPDATE_BEGIN`（总长 + SHA-256），随后按 **1 KB 分块**推送，最后 `UPDATE_END`；
4. 服务端逐块写入 `multicastForward.exe.new`，偏移必须连续；收齐后重新计算 SHA-256 比对；
5. 校验通过 → 回 `UPDATE_RESULT(0x00)` → 拉起 `multicastForwardLauncher.exe --apply` → 主进程正常退出；
6. 启动器等待进程消失，把旧 exe 备份为 `.old`，替换，启动新进程，做 4 秒存活检测：
   - 存活：删除 `.old`，记录「更新完成」；
   - 立即退出：删除新文件，恢复 `.old`，重启旧版本，记录「已回滚」。
7. 客户端收到结果后按常规重连逻辑恢复转发。

守护模式（不带参数启动启动器）下，启动器自行拉起主程序并附加 `--autostart`；主程序更新后直接退出，启动器检测到 `.new` 即完成替换，无需再次拉起启动器。

### 2.7 启动器守护行为

启动器是部署目录里唯一常驻的进程，运行在通知区域，不显示任何窗口：

| 行为 | 说明 |
| --- | --- |
| 驻留方式 | 创建隐藏窗口承载 `Shell_NotifyIcon`，任务栏与 Alt+Tab 均不可见，避免被误关 |
| 拉起主程序 | 启动即拉起 `multicastForward.exe --autostart`，并置环境变量 `MCFW_LAUNCHED_BY_LAUNCHER=1` |
| 自动恢复 | 主程序退出后 **3 秒**重新拉起，不区分退出码；连续快速失败（启动后 5 秒内退出）按 6/12/24/30 秒退避，防崩溃风暴刷日志 |
| 接管而非重复启动 | 每轮启动前先按进程名探测，若已有同名进程（人工启动、`--apply` 刚拉起新版）则接管监控，不再起第二个实例 |
| 单实例 | 命名互斥量 `Local\McfwLauncherGuard`；重复启动只提示已运行，直接退出 |
| 退出方式 | 仅通知区域右键【退出守护】可结束（带二次确认），退出不关闭正在运行的主程序；系统关机/注销时不再拉起 |
| 托盘菜单 | 显示主程序窗口（必要时从最小化还原并置前）、打开运行日志、退出守护；双击图标等同"显示主程序窗口" |
| 日志 | 同目录 `launcher.log`：启动、退出、替换、回滚、退出码、重试间隔全部落盘 |
| 兼容 | 资源管理器重启后重新注册图标（处理 `TaskbarCreated` 消息） |

启动器刻意用 **纯 Win32 API** 实现，而不是 MFC：MFC 需要额外运行库，主程序目录一旦缺少 DLL，启动器会跟着起不来，恰恰失去"回滚"的意义。纯 Win32 只依赖系统 DLL，体积小、启动快，能保证在最坏情况下仍把旧版本拉回来。

## 3 关键机制设计

### 3.1 线程模型：单线程事件驱动

两端均为单线程 `QCoreApplication` 事件循环，不使用工作线程。

理由：

1. 峰值 100 包/秒，单核处理开销远低于 1%，多线程无收益。
2. 组播接收、TCP 发送、心跳、重连在同一线程内串行，天然无锁、无竞态。
3. 需求要求「队列写入不得阻塞接收循环」。单线程下只要所有 socket 操作非阻塞、队列操作 O(1)，该条自动满足。

代价与对策：

- 任一环节的同步阻塞都会拖垮整条链路。**禁止**在事件回调中调用 `waitForReadyRead`、`waitForConnected`、`sleep`、同步文件 IO。
- 认证失败后的 1 秒延迟必须用 `QTimer::singleShot` 实现，不能用 sleep（需求 FR-B4）。

### 3.2 背压：自管队列 + 高水位发送泵

Qt 的 `QTcpSocket::write()` 会把数据追加到内部写缓冲，该缓冲**没有上限**。如果直接「收到组播就 write」，对端不收时内存会持续增长，AC-06（背压保护）必然失败。

因此发送路径设计为三段：

```text
组播回调  --push-->  [TxQueue 有界 1024]  --pump-->  QTcpSocket 内部缓冲  -->  网络
            满则丢最旧                    仅当 bytesToWrite() < 高水位
```

发送泵规则：

| 条件 | 动作 |
| --- | --- |
| `queue` 非空 且 `socket->bytesToWrite() < HIGH_WATERMARK` | 出队一帧并 `write()`，循环 |
| `socket->bytesToWrite() >= HIGH_WATERMARK` | 暂停泵，等待 `bytesWritten` 信号再次触发 |
| 队列已满（新帧到来） | 丢弃**最旧**一帧，`dropped++`，再压入新帧 |
| 连接断开 | `queue.clear()`，避免重连后补发旧包（见 Q4） |

参数取值：

- `HIGH_WATERMARK` = 64 KB。约等于 60 帧，足够覆盖一次事件循环内的突发。
- 队列容量默认 1024 帧，可配。内存上界 ≈ 1024 × (1027 + 32) ≈ 1.08 MB。

这套设计的实质是：**把「无界」变成「两级有界」**——队列有界负责丢包，socket 缓冲由高水位钳住，从而保证内存恒定。

### 3.3 组播接收与过滤（FR-A1 / AC-07 / AC-12）

接收 socket 的处理顺序：

1. 绑定：**待定**，见 Q1。方案一为 `0.0.0.0:port` + 目的地址过滤；方案二为直接绑定组播地址。
2. 入组：`joinMulticastGroup(group, iface)`，`iface` 由配置的网卡 IPv4 反查得到。**不得**依赖默认路由，也**不得**把 socket 绑到网卡 IP（那样会收不到组播）。
3. 收包：`pendingDatagramSize()` 先取真实长度，再决定是否读取。
   - `len == 0` → 丢弃，`droppedZero++`。
   - `len > 1024` → **不读取载荷**，直接丢弃，`droppedOversize++`。此路径满足 AC-07。
   - 其余 → `readDatagram()` 读入，检查 `destinationAddress()` 是否为配置组地址，不符则丢弃并 `droppedWrongGroup++`（AC-12）。
4. 通过过滤后，按协议封装为 DATA 帧压入队列。

> 注意：此处不能用固定 1024 字节缓冲去读。固定缓冲会把 1025 字节的包静默截断成 1024，导致 AC-07 失效且载荷被篡改——这违反「逐字节一致」的核心要求。

### 3.4 连接状态机（主机 A）

```text
        start
          |
          v
     [Idle] --connect()--> [Connecting]
                                 | 连接成功
                                 v
                            [Handshaking] --AUTH_RESULT 0x00--> [Running]
                                 |                                     |
                                 | 失败/超时                            | 断线/PONG 连续超时
                                 v                                     v
                             [Backoff] <-------------------------- [Backoff]
                                 | 退避到期
                                 +--> [Connecting]
```

| 当前状态 | 事件 | 下一状态 | 动作 |
| --- | --- | --- | --- |
| Idle | `start()` | Connecting | `connectToHost` |
| Connecting | 连接成功 | Handshaking | 发 HELLO，启动 5s 握手定时器 |
| Connecting | 连接失败 | Backoff | 记录，3 秒后重试 |
| Handshaking | 收到 16B CHALLENGE | Handshaking | 计算 HMAC，发 AUTH |
| Handshaking | 收到 `0x00` | Running | 停握手定时器，启动心跳，恢复发送泵 |
| Handshaking | 收到 `0x01` | Backoff | error 日志，按**最大**退避间隔重试 |
| Handshaking | 5s 超时 / 断线 | Backoff | warn 日志 |
| Running | 收到 PONG | Running | 清零未响应计数 |
| Running | 连续 3 次 PING 无 PONG | Backoff | 主动 `abort()` |
| Running | 断线 | Backoff | 清空队列 |
| Backoff | 定时器到期（3 秒） | Connecting | — |
| 任意 | `stop()` | Idle | 关闭 socket，打印一行摘要 |

重试策略：连接失败/断开后**固定每 3 秒重试一次**，不做指数退避；连续失败只记一条 warn（`连接不可用…每 3 秒重试一次`），后续尝试降为 debug，避免日志刷屏。认证失败仍按 `reconnect_max`（默认 30 秒）重试，防止口令被暴力猜测。

### 3.5 会话状态机（主机 B）

单活动会话，但**允许并存的握手中连接**——因为「新连接认证成功后才替换旧连接」，一个正在认证的新连接不能挤掉正在工作的旧会话。

```text
LISTENING --accept()--> [Handshaking]
                             | AUTH 成功
                             v
                        [Active] --替换-->  旧 Active 被关闭
                             |
                             | 心跳超时 / 断线 / 非法帧
                             v
                         [Closed] --> LISTENING
```

规则：

| 编号 | 规则 |
| --- | --- |
| S1 | 握手中连接上限 8 个，超出时拒绝新连接（`maxPendingConnections` + 自管计数），防止认证型 DoS |
| S2 | 仅当 AUTH_RESULT 发送 `0x00` 后，才把该连接提升为 Active |
| S3 | 提升顺序：**先**把新连接设为 Active，**再**关闭旧连接。避免中间出现无活动会话的窗口 |
| S4 | 旧连接关闭回调中必须判定「我是否仍是当前 Active」，否则会把新会话误清空。这是本设计最容易踩的坑 |
| S5 | Active 会话记录最后收到任意帧的时间，超 `heartbeat_timeout` 主动关闭 |
| S6 | 任一连接出现非法帧，只关闭该连接，不影响监听和其他会话 |

### 3.6 心跳

| 侧 | 行为 | 参数 |
| --- | --- | --- |
| A | 每 `heartbeat_interval`（10s）发 PING；连续 3 次未收到 PONG 判定失效 | 30s |
| B | 收到 PING 回 PONG；超过 `heartbeat_timeout` 未收到任何帧则关闭 | 30s（建议 40s，见 Q2） |

心跳在 Running 状态下启动，进入 Backoff / Idle 时停止。

**已知隐患**：两端阈值相等（均 30s），网络抖动时可能同时判定对端死亡，日志会互相矛盾，不利于排障。建议 B 侧取 40s，由 A 先发现并主动重连，行为更确定。

### 3.7 口令与脱敏

- 口令以 UTF-8 字节作为 HMAC key，不做 Unicode 规范化。
- 启动校验：口令为空直接退出；非 ASCII 字符时输出 warn（两端文件编码必须一致）。
- 日志与统计中：口令**永不输出**；HMAC 值最多输出前 3 字节 + `...`，或仅输出长度。
- 进程参数不接收口令（避免 `ps` 泄露），只从配置文件读取；若命令行出现 `--password` 则拒绝启动并提示。

## 4 接口设计

### 4.1 命令行接口

两端统一：

```text
mc_forward_a -c <配置文件> [--log-level <error|warn|info|debug>] [--version] [--help]
mc_forward_b -c <配置文件> [--log-level <...>] [--version] [--help]
```

| 参数 | 说明 |
| --- | --- |
| `-c, --config` | 配置文件路径，默认 `mc_forward.ini`（当前目录） |
| `--log-level` | 覆盖配置文件中的 `runtime.log_level` |
| `--version` | 打印版本并退出 |
| `--help` | 打印用法并退出 |

优先级：命令行 > 配置文件 > 内置默认值。**口令不提供命令行参数。**

退出码：

| 码 | 含义 |
| --- | --- |
| 0 | 正常退出（收到 SIGINT/Ctrl+C） |
| 1 | 配置错误（文件缺失、字段非法、口令为空） |

## 5 数据结构设计

### 5.1 配置结构

```cpp
struct Config {
    enum Role { Client, Server };
    struct Multicast { QString group; quint16 port = 0; QString ifaceAddr; };
    struct Server    { QString host; quint16 port = 0; };   // A 侧用
    struct Listen    { QString host = "0.0.0.0"; quint16 port = 0; }; // B 侧用

    Role    role;
    Multicast mc;
    Server  server;
    Listen  listen;

    int queueSize        = 1024;
    int reconnectMinSec  = 1;
    int reconnectMaxSec  = 30;
    int heartbeatIntervalSec = 10;   // A
```

启动校验项（任一失败即退出，码 1）：

| 项 | 规则 |
| --- | --- |
| 组播地址 | 必须为 IPv4 单播以外的合法组地址；合法范围 `224.0.1.0`–`239.255.255.255`；拒绝 `224.0.0.0/24`（本地链路，TTL 必须为 1，转发会异常） |
| 端口 | 1–65535，且 `multicast.port` 与 `listen.port` 不得为 0 |
| 网卡 | `multicast.interface` 必须能反查到 `QNetworkInterface`，否则报错并列出可选地址 |
| 口令 | 非空；长度 <8 时告警 |
| TTL | 1–255 |
| 同机环路 | 若 A 的 `group:port` 与 B 的 `group:port` 相同且 `loop=true`，告警 |

### 5.2 帧与缓冲

| 结构 | 说明 | 上界 |
| --- | --- | --- |
| 帧 | `1B type + 2B length + payload` | 1027 B |
| 队列元素 | 完整帧的 `QByteArray` | 1024 个 |
| 解帧缓冲 | TCP 字节流累积区 | 4 KB，超过且解不出帧即判非法 |

## 6 出错处理设计

### 6.1 错误分类

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 致命启动错误 | 配置非法、端口占用、入组失败 | 打印明确原因，退出码 1/2 |
| 可恢复连接错误 | 连接被拒、对端 RST、心跳超时 | 转入 Backoff，日志限频 |
| 单包错误 | 超长包、发送失败 | 丢弃并计数，不上抛，不断连接 |
| 协议错误 | 非法帧、认证失败 | 断开该连接，记录日志 |

### 6.2 日志限频

A 侧在 Backoff 状态下重连失败会持续产生日志。策略：同一原因的错误日志，前 3 次全量输出，之后每 60 秒最多 1 条，退出 Backoff 时重置计数。避免日志刷爆磁盘。

### 6.3 恢复策略

| 场景 | 恢复方式 | 人工介入 |
| --- | --- | --- |
| B 重启 | A 自动重连 | 否 |
| 网络中断 | A 自动重连，队列中的旧包丢弃 | 否 |
| 口令不一致 | A 按最大退避重试，日志提示「疑似口令不一致」 | 是 |
| 端口被占用 | B 启动失败退出 | 是 |
| 组播入组失败 | 启动失败，提示网卡与组地址 | 是 |
| 进程崩溃 | 由启动器（`multicastForwardLauncher.exe`）3 秒后自动拉起；启动器本身崩溃需外部（计划任务）拉起 | 需与启动器配套部署 |

## 7 设计决策与取舍

| 编号 | 决策 | 备选方案 | 理由 |
| --- | --- | --- | --- |
| D-01 | C++17 + Qt 5.15（Core、Network）+ CMake | MFC；裸 Winsock；Go | MFC 是 GUI 框架、无跨平台、本机未装组件；裸 Winsock 需自行实现 INI/HMAC/事件循环；Go 需额外工具链 |
| D-02 | 单线程事件驱动 | 收包线程 + 发送线程 | 100 包/秒无性能压力；单线程无锁、无竞态，代码量与缺陷面显著更小 |
| D-03 | 自管有界队列 + 写高水位 | 直接 `QTcpSocket::write()` | 后者内部缓冲无界，AC-06 必失败 |
| D-04 | 队列满丢最旧 | 丢最新（尾丢弃） | 实时性优先，旧包补发对组播业务无意义 |
| D-05 | 不引入应用层序号 | 每帧带 32 位序号 | TCP 已保证有序可靠，序号无额外价值，只增加 4 B/包开销与实现复杂度 |
| D-06 | 帧头固定 3 字节 | 变长头 / TLV | 载荷上限 1024，2 字节长度足够；固定头解析最简单 |
| D-07 | 握手用定长字段，不套帧格式 | 握手也走 `type+len+payload` | 握手字段长度全固定，套帧格式反而多一层解析 |
| D-08 | B 侧允许并存多个握手中连接 | 全局仅 1 个 TCP 连接 | 若只有 1 个，新连接会在认证前挤掉正在工作的旧会话，与 D4「认证成功后替换」矛盾 |
| D-09 | 日志自研薄封装 + `qInstallMessageHandler` | 直接调用 `qDebug` | 需要分级、脱敏、双输出、限频；`qDebug` 无法统一控制，且会污染输出格式 |
| D-10 | 网卡用 IPv4 地址标识 | 网卡名称 | Windows 网卡名可能是中文「以太网」，Qt 的 `interfaceFromName` 需内部名（GUID 形式），两者不通用；按地址反查唯一且跨平台一致 |

### 9.1 环境实测结论（2026-11-19）

| 结论 | 依据 |
| --- | --- |
| 工具链可用 | MSVC 19.51 + Qt 5.15.2(msvc2019_64) + CMake + Ninja 构建通过 |
| HMAC 实现一致 | `QMessageAuthenticationCode` 与 OpenSSL 对同一测试向量的结果完全一致 |
| 不能绑定组播地址 | 六个网卡逐一尝试，均为 `The address is not available` |
| 目的地址可获取 | 单播自检中 `QNetworkDatagram::destinationAddress()` 分别返回 `127.0.0.1`、`172.16.9.1`，IP_PKTINFO 通道可用 |
| 组播入组成功 | `netsh interface ipv4 show joins` 中目标接口出现配置的组地址 |
| **入站组播被防火墙拦截** | 发出成功（`writeDatagram` 返回完整长度）但本机收不到；同一 exe 的单播回环正常，而三档防火墙均为 Enabled + 默认拒绝入站 |

### 9.2 本机自测需额外放行（重要）

Windows 防火墙默认拦截入站 UDP，会导致「组播入组成功但一包都收不到」。自测前需以管理员身份执行：

```bat
netsh advfirewall firewall add rule name="mc_forward_a" dir=in action=allow ^
  program="<仓库路径>\build\mc_forward_a.exe" enable=yes profile=any
```

主机 B 只发不收，不需要放行。现场部署时应改为按端口/网段放行，而非按程序放行。

### 9.3 Qt 日志的两个坑（已规避）

1. 无控制台时（stdout 被重定向到管道）Qt 默认处理器会把日志送到 `OutputDebugString`，导致重定向后日志为空。Log 模块自行 `fwrite(stderr)`，不受此影响。
2. `QHostAddress(QHostAddress::AnyIPv4)` 的构造函数是 explicit，`bind()` 必须显式构造，不能直接传枚举值。

协议层面的待确认项见《协议规格》附录 A。
